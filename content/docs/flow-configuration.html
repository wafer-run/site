Flow Configuration

Auto-Discovery

Impresspress scans flows/**/*.json under its working directory on startup and loads every file it finds as a flow definition (in builds with WASM block support). No explicit registration is required — drop a .json file anywhere under flows/ and it is picked up on the next restart. A file that does not parse or validate is skipped with a warning naming it.

flows/
  api.json
  admin/panel.json

Each file holds one WaferFlow document. Its id names the flow — the file path is used only for discovery.

A flow is an ordered list of steps, each naming a block to run:

{
    "id": "api",
    "name": "API",
    "version": "0.1.0",
    "steps": [
        { "id": "security-headers", "block": "wafer-run/security-headers" },
        { "id": "cors",             "block": "wafer-run/cors" },
        {
            "id": "router",
            "block": "wafer-run/router",
            "config": {
                "routes": [
                    { "path": "/api/hello", "actions": ["retrieve"], "block": "hello" },
                    { "path": "/api/users", "actions": ["create"], "block": "create-user" },
                    { "path": "/api/items/{id}", "block": "items" },
                    { "path": "/api/files/**", "block": "file-handler" }
                ]
            }
        }
    ],
    "config": { "on_error": "stop" }
}

Steps run in order. A step whose block halts (answers and stops the flow), drops the request, or errors under "on_error": "stop" ends the flow; otherwise the next step runs — a middleware block passes the request through, and a responding block's output becomes the body the next step sees. For most apps, use wafer-run/http-server, which sets up the full infrastructure chain automatically — see Built-in Blocks. Custom flows let you compose blocks in any order.

Routing

Request routing is the wafer-run/router block's job, configured by its routes list. The first route that matches wins:

  • path — the path to match; {var} captures a segment (available as req.param.var in meta) and a trailing /** matches any remaining segments
  • block — the block the request is dispatched to
  • actions (or methods) — optional list of actions or HTTP methods the route accepts; omit it to accept any

A step's next list routes between steps on when conditions over step outputs — see the spec.

Flow Config

The top-level config object supports:

  • on_error — error policy: "stop" (abort the flow, the default) or "continue" (record the failed step's output as null and go on)
  • timeout — flow timeout (e.g. "250ms", "30s", "5m", "2h"; a bare number is seconds), at most 24 hours
  • timeout_ms — the same timeout in milliseconds; set at most one of timeout and timeout_ms
  • max_steps — cap on step executions (default 1000)

Any other key or on_error value is refused when the flow is loaded. See the WaferFlow Spec for the full field list.

Step Config

A step's config object is passed to its block for that step only, over the block's flow- and instance-level config:

{
    "id": "check-role",
    "block": "acme/role-check",
    "config": { "role": "editor" }
}

The block reads these values with ctx.config_get("role").
